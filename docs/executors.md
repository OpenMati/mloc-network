# Executor Matrix and Dependency Layers (2025-10-09, Author: Codex)

This document summarizes the available executors on the worker side, their corresponding `taskType`, optional dependencies to install, and output specifications, making it easier to select appropriate installation packages and templates for different scenarios.

## 1. Quick Reference Table

| taskType        | Executor Class        | Dependency Layer (extras) | Description |
| --------------- | --------------------- | ------------------------- | ----------- |
| `echo`          | `EchoExecutor`           | Built-in, no extra dependencies | Simple validation executor for smoke tests and script verification, outputs echo. |
| `inference`     | `HFTransformersExecutor` | `mloc[inference]`         | Default CPU inference path, outputs `responses.json`; can enable `vllm` if GPU is available. |
| `inference`     | `VLLMExecutor`        | `mloc[inference]` + GPU   | Requires available CUDA/GPU, auto-detected at runtime. |
| `rag`           | `RAGExecutor`         | `mloc[rag]`               | Depends on Qdrant/fastembed, query results written to `artifacts/`. |
| `agent`         | `AgentExecutor`       | `mloc[agent]`             | Integrates youtu-agent, requires OpenAI/Google API credentials. |
| `sft`           | `SFTExecutor`         | `mloc[training]`          | TRL-based supervised fine-tuning, outputs checkpoint to `artifacts/`. |
| `lora_sft`      | `LoRASFTExecutor`     | `mloc[training]`          | LoRA incremental training, outputs LoRA weights and logs. |
| `ppo`           | `PPOExecutor`         | `mloc[training]`          | Requires GPU; depends on `ray`/`trl`/`deepspeed`. |
| `dpo`           | `DPOExecutor`         | `mloc[training]`          | Same as above, executes DPO process. |

> **Tip**: CPU baseline deployment only requires `pip install mloc[inference]`. Other extras can be combined as needed, e.g., `pip install mloc[inference,rag]`.

## 2. Directory and Manifest Specification

All executors write to the results directory according to the following structure:

```
<RESULTS_DIR>/<task_id>/
├── responses.json           # Main results
├── manifest.json            # Index generated by orchestrator.manifest_utils
├── logs/                    # Execution logs (can be empty)
└── artifacts/               # Additional artifacts like checkpoints, retrieval data, etc.
```

`manifest.json` automatically updates status based on `spec.output.artifacts` declared in the template:

- If an artifact has not been generated, the `status` in manifest is marked as `missing` for debugging.
- HTTP upload interface writes attachments to `artifacts/` and syncs manifest.
- Aggregation tasks refresh manifest when parent and child tasks complete, ensuring idempotency.

## 3. Installation Examples

```bash
# Run only orchestrator + CPU worker
pip install mloc[inference]

# Enable RAG and Agent pipelines
pip install mloc[inference,rag,agent]

# Complete training stack (SFT / LoRA / PPO / DPO)
pip install mloc[inference,training]
```

## 4. Runtime Fallback Strategy

- `worker/executors/__init__.py` uses on-demand import strategy, missing dependencies are logged in `IMPORT_ERRORS` and printed by `worker/main.py`.
- GPU-related executors check `torch.cuda.is_available()` during initialization, automatically skipping if unavailable.
- If core `HFTransformersExecutor` is missing, worker startup will abort and prompt to install `mloc[inference]` extras.

## 5. Template Writing Notes

1. Clearly map `spec.taskType` to executors in the table, avoiding typos.
2. List expected artifacts in `spec.output.artifacts` (e.g., `artifacts/checkpoint.pt`, `logs`). Manifest validates based on this list.
3. For data-parallel tasks, ensure `spec.parallel.enabled` is set correctly; aggregator validates that all shard results are complete.

---

To extend new executors, follow the conventions in this table: define dedicated extras for new executors, supplement template examples, and register them in code via `EXECUTOR_REGISTRY` for unified fallback behavior.
